# poly-file-manager

> Multilingual: [English](#poly-file-manager) | [中文](#poly-file-manager-中文)

> Apart from the core logic, most of the code in this project was generated by AI

## Description

`poly-file-manager` is a tag-based file organizer. It does **not** copy or move
files: it only records which tags belong to which paths and maintains a
"repository" directory that mirrors that relation with per-tag folders. Inside
every tag folder it places a Windows shortcut (`.lnk`) or, on other platforms, a
symbolic link pointing at the real file, so your operating system's file manager
can browse the same file under several logical categories.

## Features

- Attach one or more tags to any file or directory path.
- Query files that carry all of a set of tags, or tags shared by a set of files.
- Keep a repository directory whose sub-folders are tags and whose links are the
  associations.
- Work **like git**: run `pfm` anywhere inside a repository and it is found
  automatically by walking up the directory tree (at most 5 levels).
- Validate and re-synchronize the data with the on-disk repository in either
  direction (data → repository, or repository → data).
- Support Windows shortcuts via the COM Shell Link API and POSIX symlinks.

## Architecture

Built with C++23 and layering each concern into a dedicated class:

| Layer | Responsibility |
| --- | --- |
| `BiMap` | Generic two-domain, many-to-many relation stored on stable `shared_ptr` identities. Query/associate/rename in O(log n). |
| `DataManager` | Domain wrapper around `BiMap` for tags and paths, plus conversion to/from the compact `FileTagData` transfer format. |
| `FileManager` | Repository folder layout: category (tag) directories and the links inside them. |
| `LinkManager` | Platform-neutral creation/removal/`resolve` of links (`.lnk` shortcuts on Windows, symlinks elsewhere). |
| `Serializer` | Stateless `FileTagData` ↔ JSON conversion and stateful read/write of the hidden data file, including hidden-attribute handling on Windows. |
| `PolyFileManager` | Facade that keeps data and repository in lock-step, with rollback on partial failure. |

Persisted state lives in a hidden file named `.poly_file_manager` (JSON) inside
the repository directory.

## Build

### Requirements

1. **CMake ≥ 3.20**.
2. A **C++23** capable compiler — MinGW-w64 GCC 13.1+ on Windows, GCC/Clang on POSIX.
3. **Qt 6** (Widgets) for the GUI, plus the MinGW toolchain **that matches your
   Qt kit** (which is required to avoid ABI/runtime mismatches).

### Building the core + CLI (no GUI)

Configure and build the reusable core library and the `pfm` command-line tool.
On Windows make sure your MinGW is first in `PATH`; pass the generator on
Windows.

```sh
cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release   # Windows
# cmake -S . -B build -DCMAKE_BUILD_TYPE=Release                      # POSIX
cmake --build build --target poly_core   # core static library
cmake --build build --target pfm         # command-line tool
```

Add the built `pfm` to your `PATH` to use it anywhere.

### Building the Qt GUI

The GUI is built automatically when CMake finds Qt 6 (`Widgets`). Point CMake at
your Qt kit with `-DCMAKE_PREFIX_PATH=<Qt>/mingw_64`. **Use the MinGW that Qt was
built with** (e.g. `C:\Qt\Tools\mingw1310_64\bin` for a default Qt 6.11 install,
or `C:\Qt\<version>\mingw_64\bin` from a Qt command prompt); put it first on
`PATH` so CMake picks it. Mixing in another MinGW causes a runtime `libstdc++`
"cannot locate entry point" error.

On Windows (from a Qt command prompt, or with the matching MinGW on `PATH`):

```sh
set PATH=C:\Qt\Tools\mingw1310_64\bin;C:\Qt\6.11.2\mingw_64\bin;%PATH%
cmake -S . -B build_gui -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release `
      -DCMAKE_PREFIX_PATH=C:/Qt/6.11.2/mingw_64
cmake --build build_gui --target qt_gui
```

`qt_gui` links against `poly_core` and, after the build, `windeployqt` copies the
Qt runtime DLLs next to the executable so it can be started directly.

> **No Qt installed?** Set `-DBUILD_GUI=OFF` (or simply don't have Qt on the
> machine) to build only the core library and CLI. The core and CLI need no Qt.

> **Qt Multimedia (optional)**: used only for video thumbnails. If your Qt kit
> lacks Multimedia, the GUI still builds — videos just show a file-type icon
> instead of a frame. On the default Qt 6.11 install Multimedia is present.

### Convenience script

`build_gui.bat` (Windows) wraps the GUI build above. It uses `QTDIR` and
`QT_MINGW` environment variables; see the notes inside the script if your Qt is
elsewhere. The documented `cmake` flow is the canonical way to build.

The build produces:

- `libpoly_core.a` — the reusable static library of the core domain classes.
- `pfm.exe` — the command-line tool, linking against `poly_core`.
- `qt_gui.exe` — the Qt Widgets front-end (only when Qt 6 is found).

### Packaging a Windows release

A portable "green" Windows ZIP can be built with `build_release.bat`:

```bat
set QTDIR=C:\Qt\6.11.2\mingw_64
set QT_MINGW=C:\Qt\Tools\mingw1310_64\bin
build_release.bat
```

It builds `pfm` and `qt_gui`, gathers the executables plus the Qt/MinGW runtime
into `dist/`, and zips them to `poly-file-manager-<VERSION>-win64.zip`. Extract
and run `qt_gui.exe` (or use `pfm.exe` from a terminal).

For an automated **GitHub Release**, push a version tag (`v*`); the workflow in
`.github/workflows/release.yml` builds on Windows, packages the portable ZIP and
attaches it to the Release (see your repo's Releases page). Relevant files:

- `build_release.bat` — local packaging script.
- `.github/workflows/release.yml` — CI build + Release upload.

## Usage

A repository is a directory that contains the hidden `.poly_file_manager` data
file. `pfm` finds it automatically: starting from the current directory it walks
up until it finds a repository. Use `--repo <path>` to point at one explicitly
and skip auto-detection.

### Repository lifecycle

```sh
# Create a repository in the current directory (or use --repo <path>)
pfm init

# Delete a repository (removes the data file and all tag folders)
pfm destroy --yes
```

### Managing tags and paths

```sh
pfm tag add work urgent     # add tags
pfm tag rm work             # remove tags
pfm tag mv urgent important # rename a tag
pfm tag ls                  # list all tags

pfm path add /data/a.txt /data/b.txt   # register paths
pfm path rm /data/a.txt                # remove a path
pfm path mv /data/a.txt /data/a2.txt   # replace a registered file path
pfm path ls                            # list all registered paths
```

### Linking tags to paths

`assign` creates the association (and, for convenience, registers the tag and the
path first if they are missing). `unassign` drops it.

```sh
pfm assign docs /data/a.txt /data/b.txt
pfm assign urgent /data/a.txt
pfm unassign docs /data/b.txt
```

### Queries

```sh
# Files carrying ALL of the given tags
pfm files docs urgent

# Tags shared by the given paths (a single path yields all of its tags)
pfm tags /data/a.txt
pfm tags /data/a.txt /data/b.txt

# All tags / all paths
pfm tag ls
pfm path ls
```

### Consistency and synchronization

```sh
# Do the data and the on-disk repository agree?
pfm check

# Rebuild the repository (tag folders + links) to match the data. Default direction.
pfm sync
pfm sync --to-repo

# Rebuild the data to match the on-disk repository.
pfm sync --from-repo
```

`check` exits `0` when consistent and `1` when it is not, which is useful in
scripts.

## Repository layout

```
<repo>/
  .poly_file_manager          # hidden JSON data file
  docs/                       # a tag becomes a folder
    a.txt.lnk                 # a link/shortcut pointing at the real file
  urgent/
    a.txt.lnk
```

# poly-file-manager 中文

## 描述

`poly-file-manager` 是一个按标签对文件进行分类与管理的工具。它**不会**复制或移动文件：只记录"哪些标签对应哪些路径"，并维护一个"仓库"目录来镜像这一关系。仓库中的每个标签是一个子目录，目录里为每个关联文件放置一个 Windows 快捷方式（`.lnk`，其他平台为符号链接），指向真实文件——这样操作系统文件管理器就能在多个逻辑分类下浏览同一文件。

## 功能特性

1. 为一个文件或目录路径附加一个或多个标签。
2. 查询同时具有若干标签的文件，或若干文件共同具有的标签。
3. 维护仓库目录：子目录是标签，目录内链接是关联关系。
4. **像 git 一样**：在仓库目录内（或其子目录）直接运行 `pfm` 即可，程序会向上查找仓库（最多 5 层）。
5. 校验并双向同步数据与磁盘仓库（数据 → 仓库，或仓库 → 数据）。
6. 支持 Windows 快捷方式（COM Shell Link API）与 POSIX 符号链接。

## 架构

基于 C++23，各职责独立成类：

| 层 | 职责 |
| --- | --- |
| `BiMap` | 通用双域多对多关系，基于稳定 `shared_ptr` 身份，查询/关联/重命名 O(log n)。 |
| `DataManager` | 面向标签与路径的 `BiMap` 领域封装，以及与紧凑格式 `FileTagData` 的互转。 |
| `FileManager` | 仓库目录布局：分类（标签）目录及其中的链接。 |
| `LinkManager` | 跨平台统一创建/删除/解析链接（Windows 为 `.lnk` 快捷方式，其他为符号链接）。 |
| `Serializer` | 无状态的 `FileTagData` ↔ JSON 转换，以及有状态的数据文件读写（含 Windows 隐藏属性处理）。 |
| `PolyFileManager` | 门面类，保证数据与仓库一致，并在部分失败时回滚。 |

持久化数据存放在仓库目录下的隐藏文件 `.poly_file_manager`（JSON）。

## 使用方法

仓库是一个包含隐藏数据文件 `.poly_file_manager` 的目录。`pfm` 会**自动检测**：从当前目录向上逐级查找（最多向上 5 层），直到找到仓库。也可以用 `--repo <路径>` 显式指定，跳过自动检测。

### 仓库生命周期

```sh
# 在当前目录创建仓库（或用 --repo <路径>）
pfm init

# 删除仓库（移除数据文件与所有标签目录）
pfm destroy --yes
```

### 管理标签与路径

```sh
pfm tag add work urgent      # 新增标签
pfm tag rm work              # 删除标签
pfm tag mv urgent important  # 重命名标签
pfm tag ls                   # 列出所有标签

pfm path add /data/a.txt /data/b.txt   # 登记路径
pfm path rm /data/a.txt                # 移除路径
pfm path mv /data/a.txt /data/a2.txt   # 替换文件路径
pfm path ls                            # 列出所有已登记路径
```

### 建立标签与路径的关联

`assign` 会建立关联（为方便起见，若标签或路径缺失会先自动登记）；`unassign` 取消关联。

```sh
pfm assign docs /data/a.txt /data/b.txt
pfm assign urgent /data/a.txt
pfm unassign docs /data/b.txt
```

### 查询

```sh
# 同时具有所有给定标签的文件
pfm files docs urgent

# 这些路径共同具有的标签（单个路径则返回其全部标签）
pfm tags /data/a.txt
pfm tags /data/a.txt /data/b.txt

# 所有标签 / 所有路径
pfm tag ls
pfm path ls
```

### 一致性校验与同步

```sh
# 数据与磁盘仓库是否一致？
pfm check

# 按数据重建仓库（标签目录 + 链接）。默认方向。
pfm sync
pfm sync --to-repo

# 按磁盘仓库重建数据。
pfm sync --from-repo
```

`check` 一致时退出码为 `0`，不一致时为 `1`，便于脚本使用。
